What I learned

What coding with AI taught me

I use Claude Code every day as the builder. These are the rules I work by now. Each one cost me something before I wrote it down.

A model's summary of its own work is not evidence.

I judge a change by what I can see: the diff, the test output, the live page. If a worker says a test passed, I open the run.

A test must be able to fail.

New tests run against the old code first and must fail there for the right reason. Then I break the changed code on purpose (mutation testing) to make sure the tests notice.

Made-up data proves nothing.

Counts and populations come from production, read-only, over a connection that has first proved it cannot write. Data I invent only proves the invention.

When a check cannot run, stop. And a test must never be able to write to production.

My checking scripts stop and say so when something is missing. Once, a test reached a real write path on production. Since then tests call pure functions with read-only credentials.

Two models that disagree catch more than one that agrees.

Gemini and GPT find different kinds of mistakes in the same change. Where they disagree is where I look. I decide, and when I reject a critique I write down why, so it is not raised again.

Give the AI the whole brief, then check its work before it ships.

The brief carries the file paths, the rules and the tests to add. The worker never pushes, deploys or sends anything. I read what it made, then I merge, deploy and reply.

Saved is not the same as shown.

A row in the database and what the ops lead sees on screen are two different facts. Every UI change is checked in a signed-in browser at the user's own screen size before I say it is live.

Write everything down.

Every promise to a stakeholder gets a dated line in a ledger. Every message I send gets a record of what went out and what came back. Someone in another time zone can pick up the work from the repository.

The stack

Ordinary tools, typed, cheap at this size

Each piece was chosen for a small team that needs the system to be right more than it needs it to be clever.

Backend

Python, FastAPI, Pydantic, asyncpg. One language for the service, the tooling and the checking scripts. Typed data at every boundary.

Data

PostgreSQL on Cloud SQL, with pgvector where search needs it. Managed backups, real transactions, and row versions an undo can check against.

Runtime

Google Cloud Run, Cloud Scheduler, Secret Manager, Pub/Sub. Scales to zero, rollback is a traffic switch, and the client already ran on Google Workspace.

Frontend

Next.js, React, Tailwind on Vercel. A portal people log in to and an installable web app for the field. Playwright for signed-in checks against the real deployment.

Models

Gemini in production for classifying posts and drafting replies. Two workloads on Llama 3.3 through an OpenRouter gateway, so changing a model is a config change. Personal data is scrubbed before anything goes to a model.

Tooling

Claude Code as the daily builder. MCP servers I wrote (the review gate) and ones I use (Playwright). pytest with mutation testing. Git, gcloud.

Why not n8n or Make: these integrations move money, door codes and guest data. Every write path needs to be code I can test, replay and roll back.

Quality

What a change goes through before anyone sees it

Every non-trivial change takes the same path. This is the real order, and each step leaves something I can show.

flowchart LR
  A[Brief: paths, rules, tests] --> B[Build on a branch]
  B --> C[New tests fail on the old code]
  C --> D[Break the code on purpose; tests must notice]
  D --> E[Two-model review: Gemini + GPT]
  E --> F[Secret scan on every file that leaves]
  F --> G[Merge; check the build matches git]
  G --> H[Signed-in check at desktop and phone width]
  H --> I[Record, ledger line, reply]
  • Testing. About 4,900 backend tests. A write path is rehearsed on a real throwaway Postgres, including two deliveries of the same event, lock waits, a lost commit reply and a killed connection, so the failure paths are run, not described.
  • Review. Risky changes (database writes, messages to guests or owners, money, access) get up to two paid rounds of the two-model review. Everything else gets one reviewer told to find fault. What survives is my call, and the remaining risks are written down.
  • Security. Secrets live in Secret Manager and the environment, never in code or chat. A scan refuses any file that looks like it carries a key before it leaves the machine. Door codes are encrypted at rest (AES-256-GCM). The service acts as one named Google Workspace account with a fixed list of permissions. Production checks run read-only and begin with a small test write inside a transaction that is always rolled back; the database must reject it before anything else runs.
  • Deploys. Only from a tree that matches the remote exactly. Traffic always sits fully on the latest healthy revision. A check compares the uploaded build with the files in git, so an untracked file cannot slip into an image. Environment changes are merged, never replaced. A revision that fails to start never takes traffic.
The review gate

The two-model review gate, and what it costs

Before a non-trivial commit, a Gemini auditor and a GPT auditor read the same change through an MCP server I wrote. Both must pass. They find different kinds of mistakes, so the places where they disagree are the places worth reading. I decide. A critique I reject is written down so it is not raised again.

How a review runs

  • Paths, not pasted code. The server reads the files itself. A review pack is a set of exact excerpts with each file's hash, split by topic, each part under 45 KB because the reader cuts off above that. The packs include the mutation runs, not a claim that tests exist.
  • Each round is judged on what it contains. The record of earlier actions is written truthfully, and a claim never gets stronger than its proof: local, committed, pushed, deployed and live are five different claims.
  • The only gate is both auditors passing. There is no round counter. A review that is truly stuck goes to a person.

The cost problem

The reviewers are paid API calls. A review that costs too much to run is a review nobody runs. The client's CEO agreed a monthly cap, so I built the limits into the server instead of relying on self-control:

  • Paid review only for risky changes: database writes, guest or owner messages, money, access. Everything else gets one free reviewer.
  • Two paid rounds per change. A third needs a recorded reason. The prompt names the round the guard has counted, and if the count moves between reading and sending, the request is refused at no cost.
  • An input ceiling measured against the real tokenizer. My estimate (characters divided by four) ran about 8% under the billed count (55,188 estimated against 59,816 billed), so the estimated ceiling went from 60,000 to 55,000 to keep the real prompt under the cap.
  • The risks a skipped round leaves behind are written down and carried by the person running the work.
Guard tests67 tests on the guard alone, with made-up data and no network: a temporary config and ledger, no spend rows, no balance read. Mutants M6 to M12 were each caught by the test written for them.
What it caughtThe second paid round on the backfill script found three real defects in its failure handling before it ran on production. A wording review of a message to the CEO found a button and a real record I had missed.
Pack integrityThe self-match review packs: 13 excerpts re-checked line by line against the committed files, 0 mismatches.
Known limitsThe auditors are behind on recent facts, so anything date-sensitive is checked on the web first; their design critiques still count. One auditor sometimes cuts off on long packs, which is why packs are split.
The gate is only worth having if it is cheap enough to use every time. The guard is what made it routine.
A piece of work

The self-match fix, and how I knew it worked

Mission Control turns Google Chat posts into tasks, and a reply in the thread can close or acknowledge the task. In September I traced why some tasks were closing themselves seconds after they were filed. The cause: a task's own source message could match as a reply to the task it had just created, so the system marked the task done by its creator. It had been happening quietly since March.

The fix

A real reply has a different message id from the first message in the thread. I changed the matching rule in five places so a message can never be checked against a task it created, kept real thread replies working, and made the retry path safe, because on a retry the message's own tasks already exist.

How I knew

MeasuredProduction, last eight weeks: 103 tasks closed and 462 acknowledged by their own source post. 125 closures and 93 acknowledgements came from real replies; those had to keep working. The bug dated from March, before the code was under version control.
ReplayThe new rule was run over every message the system had ever taken in, 39,375 of them: 39,008 first posts, 367 real replies, none of any other shape. No message falls outside the rule.
ReproducedThe production self-closure happened again on a throwaway local Postgres with the fix removed, and could not happen with the fix in place.
MutantsTen deliberate breaks of the fix, from reversing the rule to removing all five changes. The tests caught all ten. A control run with the database removed was refused as invalid instead of passing quietly.
Retry pathOn a retry the message's own tasks already exist, so the early checks could have matched them. All three are guarded, and removing any guard is caught by a test.
AfterDeployed the same day. The startup migration logged, and the new revision took all traffic. Nothing it had closed was reopened by code: the ops lead got a reviewed list, real open work first, with what had happened to each since, and the decision stayed with them.

The measurement and the replay mattered more than the fix. They turned "I think this is right" into numbers the ops lead could check, and they named the one change in behaviour before it shipped: status posts that used to close themselves now stay open until someone presses Done.

Changing safely

Keeping a live system changing safely

The system changes most days, with people in two time zones depending on it. Three habits carry that.

  • Data fixes are transactions with receipts. Earlier this month I rewrote 77 task titles in production. First a read-only dry run that proved the plan. Then one transaction that locked the rows, worked out every title again from the locked values, wrote a hashed before-snapshot to disk before the first UPDATE, committed, read the rows back on a separate connection and wrote a hashed receipt. A lost commit reply is settled from the server's own transaction record, never from counts. The undo restores only rows the run still owns, matched by value and row version.
  • Rollouts are snapshot, change, diff. A rollout for the field app saved a snapshot of 108 property identity rows before the deploy and compared it after the nightly sync. Exactly two rows changed, the two properties the change was meant to connect, and nothing else appeared, vanished or moved.
  • When the reviewers are right, the code changes. Two review rounds on that backfill script found three real defects in its failure handling: a false "rolled back" message if a file write failed after the commit, a hashing step that could not be resumed, and a receipt trusted for existing rather than for its contents. All three were fixed, with the failures injected on a real local Postgres, before the script touched production.
The two things I would most like to show live: the review gate reading a change, and the deploy chain refusing a tree that does not match the remote.
Studies and hours

How my studies fit NZ and Australian hours

I am in the final year of a BS in Computer Science at Ateneo de Naga University, due to finish in May 2027. Since March 2026 I have run the Pet Let work on Adelaide hours alongside it, so I know the arrangement works in practice, not only on paper.

  • Adelaide's working day starts at 06:30 my time and New Zealand's at 04:00 or 05:00, so the overlap with both sits in my morning and early afternoon.
  • My final year is thesis only. There are no classes to schedule around. I work on the thesis from home, and the only campus commitments are the defences, two a semester, four in the year. I can work full-time on NZ and Australian hours; the thesis takes the rest of the day.
